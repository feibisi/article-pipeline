## 定位重新校准

### 当前定位
WordPress 中文技术内容生产系统。

### 目标定位
**AI 原生内容生产基础设施**，WordPress 是第一个验证场景（试点），后续扩展到任何垂直领域的专业内容生产。

### 为什么要扩展
- WordPress 中文内容市场天花板明确，开发者群体有限
- 管线的核心能力，research → outline → write → review，与领域无关
- 风格系统、Trust Tier、审查模块都是通用组件
- cocobook 知识库已有多领域书籍标注，不限于 WordPress

### 扩展原则
- WordPress 先跑通，验证端到端闭环，再横向复制
- 每进入一个新领域，只需新增：领域术语表 + 品类预设微调 + 知识库索引
- 核心管线代码不为特定领域做 if-else

## 三条发展路径

### 路径 A: 纵深 — 单篇质量达到免润色发布

**目标**: 管线产出的文章不需要人工润色，直接发布。
**衡量标准**: 连续 20 篇 overall_score > 7.5 且人工审核通过率 > 80%。

#### A1: 选题过滤器（评估可行性）

对每个候选 keyword 打分：

| 维度 | 检查方式 | 权重 |
|------|----------|------|
| 素材可得性 | research 轻量扫描，3+ 独立来源 = 高分 | 0.4 |
| 观点空间 | 快速 claim 生成，有立场 = 高分，只能"介绍" = 低分 | 0.35 |
| 饱和度 | DDG/cocobook 搜同题文章数量，过多 = 低分 | 0.25 |

输出: 0-10 分。低分不自动拒绝，排到队列后面。

#### A2: 风格遵循度评分

纯规则/统计检查（不需要 LLM）：

| 风格维度 | 检查方法 |
|---------|---------|
| warmth | 人称词频（"你"/"我们"/第三人称占比） |
| density | 段落平均字数 + 标准差 |
| energy | 短句（<15字）占比 + 反问/感叹频率 |
| register | 口语标记词频率 vs 书面标记词频率 |
| edge | 判断句前置率 + "必须/一定/不是"等确定性词密度 |

输出: 各维度遵循度 0-10，加入 overall_score（权重 0.08）。

#### A3: 正向质量信号（区分"及格"与"好"）

| 信号 | 检测方法 | 说明 |
|------|----------|------|
| 开头抓力 | 前 50 字是否包含具体场景/数据/判断 | 排除"随着...的发展"类空泛开头 |
| 论据密度 | 每个 H2 段落中具体数据/代码/例子数量 | 论据质量评估 |
| 反直觉度 | 文章主张是否与 cocobook 中多数标注相反 | 相反 = 有独特观点 |
| 行动性 | 结尾是否有具体可执行的下一步 | 以可执行命令替代空泛建议 |

实现方式: 轻量 LLM 调用（用小模型做评判），非硬门控，作为 advisory 分数。

### 路径 B: 横向 — 多平台 + 选题自动化 + 领域扩展

**目标**: 稳定产出节奏，覆盖多平台，并验证非 WordPress 领域。
**衡量标准**: 月产出 8+ 篇（跨平台去重），每篇都过自动审查。

#### B1: 平台语调适配

在 style.py 新增 platform modifier 层：

```python
PLATFORM_MODIFIERS = {
    "juejin":       {"register": -0.3, "density": +0.2, "edge": +0.2},
    "v2ex":         {"register": +0.4, "warmth": +0.3, "edge": +0.1},
    "wpcommunity":  {"warmth": +0.2, "edge": -0.2},
    "linuxjoy":     {"register": -0.2, "density": +0.1},
    "wptea":        {},  # 默认
}
```

同一 outline，不同 modifier 生成不同版本。选题不变，语调自动适配。

#### B2: 选题发现机制

三条来源管线：

| 来源 | 频率 | 输出 |
|------|------|------|
| 搜索趋势 | 周更 | 新增上升关键词 → 候选队列 |
| 社区问题 | 周更 | 高频未充分回答问题 → troubleshooting/tutorial |
| 竞品内容 | 月更 | 差异化选题（他们写了我们没写的） |

每条管线输出 keyword + category 候选，过 A1 过滤器打分后排入队列。

#### B3: 领域扩展试点

第二个领域候选（按可行性排序）：

| 领域 | 优势 | 劣势 | 可行性 |
|------|------|------|--------|
| Linux/DevOps | 集群本身就是素材，赛博论坛已有内容基础 | 竞争激烈（掘金/CSDN） | 高 |
| AI 工程 | 前沿话题，cocobook 有相关标注 | 变化快，事实容易过时 | 中 |
| 独立开发者/SaaS | 文派品牌延伸自然 | 缺领域术语库和知识标注 | 中 |
| 电商技术 | weixiaoduo 有领域经验 | 与当前团队核心能力距离较远 | 低 |

建议: Linux/DevOps 作为第二试点，赛博论坛已有基础，不需要新建知识库，扩展成本最低。

#### B4: 调度器

```
每周一 06:00:
  1. 检查本周各平台计划 vs 队列可发选题
  2. 不足 → NATS 通知 modiqi 补选题
  3. 超额 → 按 priority 排序，低优先级推后
  4. 输出本周发布计划到 state.json
```

### 路径 C: 深度 — 知识驱动写作

**目标**: 让知识库成为选题发动机，产出有独特性的内容。
**衡量标准**: 每月至少 2 篇"知识冲突"驱动的文章，读者评论中出现"没想到"类反馈。

#### C1: 知识冲突发现

```
cocobook 同主题标注 → embedding 相似度聚类 → NLI 矛盾检测 → 矛盾对输出

输出示例:
- 书 A 说 "object cache 应该用 Redis"
- 书 B 说 "小站点 object cache 是反优化"
→ 选题: "WordPress Object Cache: 什么时候用 Redis 反而更慢？"
```

#### C2: 深度素材整合

当前: research 搜 cocobook → 返回相关段落 → 拼入 prompt
升级: research 搜 cocobook → 分析段落间关系（因果/例证/反例）→ 结构化素材包

| 关系类型 | 作用 | 例子 |
|---------|------|------|
| 因果链 | 合成跨书洞察 | A→B(书X) + B→C(书Y) = A→C |
| 例证集 | 挑最好的例子 | 同一论点 3 本书各有一个例子 |
| 反例库 | comparison 素材 | "但书 Z 指出了一个例外..." |

#### C3: 前置条件

- cocobook 技术类标注覆盖评估（当前 WordPress/PHP/Docker/Nginx 索引已建，其他领域？）
- NLI 矛盾检测模型评估（ailab 的 Ollama 是否有合适模型）
- 标注质量抽检（垃圾标注会产出垃圾文章）

### 路径 D: 防御 — 在 AI Slop 泛滥中建立不可替代性

**背景**: 全球每天数百万篇 AI slop 涌入搜索引擎。"不像 AI"已经不是竞争力，"有 AI slop 给不了的东西"才是。
**目标**: 每篇发布的文章至少满足一条不可替代性标准。
**衡量标准**: value_density 评分 > 6.0 方可发布；发布文章的独占信息比 > 20%。

#### Slop 的结构性弱点（我们的攻击面）

| Slop 弱点 | 原因 | 我们的对应能力 |
|-----------|------|---------------|
| 信息来源单一 | 只改写搜索前几条 | cocobook 跨书合成 |
| 无法验证 | 不运行代码 | elementary 实测环境 |
| 没有立场 | 怕错不敢判断 | Trust Tier 允许 INTERNAL 品类有观点 |
| 时间无关 | 不区分版本 | research 模块检查时效 |
| 不可回溯 | 无素材引用链 | review 交叉验证与引用追踪 |

#### D1: value_density 评分维度（加入 review 模块）

| 信号 | 检测方式 | 阈值 |
|------|----------|------|
| 独占信息比 | 文中 claim 在 DDG 前 10 结果中未出现的比例 | >20% |
| 可验证操作 | 含具体命令/代码/URL/版本号的段落占比 | >30% |
| 素材引用深度 | 引用了 cocobook 几个不同来源 | >=3 |
| 判断句密度 | 有明确立场的陈述数量 | >=2 per H2 |
| 反直觉度 | 主张与主流搜索结果相反且有证据 | >=1 |

权重: 0.12（从 humanizer 和 ai_check 各分出 0.06）。

#### D2: 选题 slop 饱和度检查（集成到 T-005 选题过滤器）

```
DDG 搜关键词 → 前 10 结果 → 分析同质度
  - 全是同质内容（标题雷同、结构雷同）→ 必须找到反直觉角度才做
  - 有空白点（某个子话题没人覆盖）→ 高优先级
  - 无同类文章 → 蓝海选题，直接做
```

#### D3: outline 强制 differentiation 字段

outline 阶段必须回答：**"这篇文章比搜索第一页的结果多给读者什么？"**

答不出来 → 不进入写作阶段。合法答案举例：
- "基于 cocobook 3 本书的交叉对比，搜索结果都只引用了官方文档"
- "包含 elementary 实测的性能数据，搜索结果都是理论描述"
- "指出了官方推荐做法在特定场景下的反效果，无人提及"

#### D4: 竞争赛道选择

| 赛道 | 策略 | 原因 |
|------|------|------|
| 深度教程（1500+字，含实测） | 主攻 | slop 做不到深度和验证 |
| 观点文（有立场+论据） | 主攻 | slop 不敢有立场 |
| 跨源综合（多书对比+实测） | 主攻 | slop 没有知识库 |
| 故障排查（真实报错+解决过程） | 副攻 | slop 编造解决方案 |
| 高搜索量通用问题 | 放弃 | slop 规模优势碾压 |
| 短生命周期热点/新闻 | 放弃 | slop 速度优势碾压 |

#### 发布必要条件（至少满足一条）

一篇文章值得发布，当且仅当：
1. 包含读者在搜索引擎前 10 结果里找不到的信息
2. 基于实测给出了可验证的具体操作步骤
3. 对一个常见做法提出了有证据的反对意见
4. 跨 3+ 来源合成了一个新洞察
5. 解决了一个现有内容没覆盖好的具体问题

如果一条都不满足，那就是 slop，不管 humanizer 分多高。

## 架构备忘：待解决的结构性问题

### S1: 审查循环成本 — 从"打回重写"到"诊断哪层坏了"

当前模式：写完 → 审查扣分 → revise → 再审查。问题：如果 writer prompt 的负面约束足够硬，ai_check 应该几乎不扣分。如果还在频繁扣分，revise 是碰运气。

改进方向：
- 第一次 ai_check < 6.0 → 不走 revise，标记为 prompt 失效
- 回溯诊断：检查负面约束是否生效、模型是否忽略 prompt、genre_rules 与负面约束是否冲突
- 审查模块输出分数及"问题出在哪一层"的归因

### S2: 模型专属风格校准

同样的 style 预设值对不同模型效果不同：
- GLM `edge: +0.6` → 攻击性判断句（过激）
- Claude `edge: +0.6` → 只是少了点 hedge（不够）

短期：不做 model-specific calibration，先用统一预设跑
长期：每个维度每个模型需要一个 calibration offset，如：

```python
MODEL_CALIBRATION = {
    "glm": {"edge": -0.1, "warmth": +0.1},   # GLM 天然激进，降一档
    "claude": {"edge": +0.1, "energy": +0.2}, # Claude 天然保守，补一档
}
```

前置条件：T-006 style_compliance 评分上线后，对同一选题用两个模型各写一篇，量化偏差再决定 offset。

### S3: 选题发生器 — 从"想写什么"到"我们有什么别人没有的"

T-005 解决"不该做什么"。缺的是"该做什么"的正向驱动。

选题发生逻辑：
1. 扫 cocobook，找标注密度最高的 topic cluster（素材充足 = 能写深）
2. 交叉 cluster-recall 中的 lesson 类型记录（真实踩坑 = 有第一手经验）
3. 每个候选自动跑轻量 research，计算独占素材数量
4. 输出："我们能写得比任何人好的 10 个话题"

与 T-005 的关系：T-005 是选题入口的过滤器（拦坏的），选题发生器是选题来源（找好的）。两者互补。

实现位置：可复用 T-005 的 `topic_filter.py`，新增 `generate_topics()` 函数。

### S4: AI 句式污染 — 写作阶段压制优于事后检测

原则：在 writer prompt 层面用硬性 negative constraints 禁止 AI 典型句式，比 review 阶段检测后打回更高效。

已实施（子代理进行中）：
- writer.py 新增 `_NEGATIVE_CONSTRAINTS` 常量，注入 prompt 末尾（最高优先级）
- 禁止清单含破折号滥用、"不是...而是..."、排比三段论、"随着...的发展"等
- check_ai_patterns() 按模型分两套权重（GLM 偏堆砌排比，Claude 偏 hedge 和破折号）

效果预期：ai_check 维度的扣分率应显著下降。如果没下降 → 回到 S1 诊断流程。
